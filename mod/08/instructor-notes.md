# Agentic engineering capstone

PDF-only revision; editable LaTeX included. Sources checked September 5, 2026.

## 1. Agentic engineering capstone

Introduce the module through the opening engineering question. Audience: undergraduate and graduate nuclear engineering students comfortable with Linux and Python.

- curriculum: User-supplied PHANES curriculum: mod/01 through mod/08/README.md.
- colors: https://umac.utexas.edu/brand-center/colors/

## 2. Choose a workflow with observable success

Kickoff session: slides 2–7. Students may propose alternatives if they can define evidence, scope and a feasible evaluation. Public-data proxies allow industry-relevant questions without assuming partner data access.


## 3. Write a question the project can answer

Ask teams to show a non-agent baseline: manual procedure, deterministic script, or lexical retrieval. The comparison should reveal where the agent adds useful capability and where it adds failure modes.


## 4. Reuse the course’s engineering artifacts

Do not ask teams to invent new incompatible record formats. They can extend the shared fields and explain the extension. Every project still uses local Linux OpenCode and its approved private endpoint.


## 5. Make milestones evidence-based

This preserves the curriculum’s 12-week active project pattern. Teams may operate within a longer semester. Milestones are acceptance checks, not just presentations of progress.


## 6. Review a proposal before coding

A strong rewrite might check a documented educational calculation package against an analytical reference and retain provenance. Avoid assuming access to licensed reactor codes or private partner geometry. A model narrowing (one input, one output, one bounded workflow) is shown in the deck (One worked approach: narrowing the proposal); it is one acceptable scope, not the required one.


## 7. Freeze an evaluation set before tuning

This prevents retrospective selection of favorable demonstrations. Teams should disclose adaptations and retain a held-out evaluation where feasible.


## 8. Run design review as an engineering exercise

Mid-project review session: slides 8–11. Bound the exercise to the project’s own test environment. It is not permission to attack external services or use real confidential data.


## 9. Four failure axes guide peer design review

These four axes synthesize the core controls of the course: physics/solver validation from module 04, orchestration bounds from module 03, security and execution permissions from module 03/05, and information-flow boundaries from module 02. Require peer teams to test at least one failure from each axis.


## 10. A useful finding is reproducible

Risk acceptance requires a named responsible reviewer and rationale. A team cannot silently mark a failure accepted because the deadline is near.


## 11. Respond to a stale-result finding

Expected: invalidate affected report/cases, bind result reuse to input and solver identity, test changed-input reuse, and rerun all results that could have mismatched provenance. Update the dossier and review response. A worked response (containment, durable fix, regression test, rerun scope) is shown in the deck (One worked approach: containing a stale result).


## 12. Make the handoff work on a clean machine

A clean rerun can use a new environment with an issued endpoint credential; do not ship actual secrets. Network access and the endpoint’s availability remain explicit deployment prerequisites.


## 13. Grade evidence and engineering judgment

Draft weights retained from the supplied curriculum. Instructor may adopt or revise them. A polished demo cannot compensate for fabricated execution evidence or an unresolved critical scope failure.


## 14. Final demonstration: show the complete chain

Require the team to show a limitation as well as a success. Reserve questions for applicability, evidence quality, configuration changes and boundary assumptions.


## 15. Example capstone acceptance contract

An example for teams to adapt, not the only permitted capstone. Set thresholds before building and preserve the distinction between tested and untested conditions.


## 16. What you should carry into engineering practice

Close by returning to the opening course question: what should an engineering agent deliver? Ask each student to name one practice they would apply to a real computational workflow.


## 17. Capstone exit ticket: defending an agentic workflow

These four final questions synthesize the entire course: calculation defense, boundary enforcement, bounded autonomy, and mandatory escalation. A model answer is shown in the deck (A complete answer: the capstone defense); grade on linking every claim directly to an inspectable artifact or contract rule.
